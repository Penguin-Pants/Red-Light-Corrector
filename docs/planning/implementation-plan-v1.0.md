## 1. Executive summary

Build a portable Windows 11 browser app with vanilla JavaScript, HTML and CSS. Evaluate a packaged classic-script entry point opened by double-clicking `index.html`, a dedicated worker with a bounded queue, a bundled HEIC decoder, and Canvas 2D for pixel access and encoding. Keep the processing core independent of the UI and build one explicit metadata export layer shared by direct-save and ZIP destinations. Each photo gets its own analysis, three correction recipes and a confidence explanation. Retain small previews and recipes, then render full-resolution selected versions one at a time at export.

Phase 1 determines whether these choices meet the baseline in Chrome on Windows 11. In particular, a browser-readable HEIC file does not establish correct HEIC orientation or color, and a successful encode does not establish preservation of EXIF/GPS or an accurate output profile. If direct launch fails a critical workflow after compatible packaging and allowed fallbacks are tried, document the failure and assess a minimal loopback launcher. All eight feasibility gates require recorded outcomes and user review before Phase 2.

## 2. Confirmed requirements and constraints

- Target Windows 11 with Chrome, fully offline with locally bundled assets. Prefer direct HTML launch. The launcher is conditional on evidence of a critical direct-launch failure.
- Accept HEIC, JPEG and PNG recursively, up to 100 eligible photos. Show names and actionable status. Process unrelated files after errors, allow cancellation and retry, and preserve input files.
- Optimize for practical natural-looking quality and responsive, bounded processing. Analyze per image, compare alternatives, offer Natural, Balanced and Aggressive, and explain low confidence and missing color evidence.
- Show a thumbnail gallery, large side-by-side preview, confidence filter, simple and advanced controls, per-image adjustments and shared settings for selected photos or the batch.
- Export selected modes to JPEG or PNG, full resolution by default, with optional resizing, flat collision-safe names and direct-folder or ZIP destinations. Preserve compatible metadata and report losses. Maintain intended orientation and color.
- Store only local preferences and named presets across sessions. Keep imported images, paths, thumbnails, file handles and per-image state in session memory. Optional local AI is a future extension.
- The specification remains authoritative. This plan proposes targets and engineering decisions for review. Phase 1, implementation and changes to the baseline each require the applicable user approval.

## 3. Proposed architecture and module boundaries

The paths below are implementation proposals for later phases. Author readable source modules and package them into local classic-script artifacts without runtime module imports. Evaluate a classic worker bootstrapped from a bundled Blob and single-threaded WASM initialized from locally packaged bytes. Keep generated artifacts and vendor notices reproducible with pinned inputs. Any eventual build tooling runs before distribution, with no runtime package manager, CDN or web service.

| Boundary | Proposed files | Contract |
| --- | --- | --- |
| Input and decode | `src/import/folder.js`, `src/imaging/loader.js`, `src/imaging/color.js` | Enumerate eligible files and retain read-only File references, session IDs and relative labels. Return canonical upright pixels with explicit working-space and orientation provenance, plus separate metadata descriptors. |
| Analysis and correction | `src/imaging/analyzer.js`, `src/imaging/correction.js`, `src/imaging/quality.js` | Analyze bounded samples. Return candidate scores, reproducible recipes, diagnostics and mode-specific confidence. Accept source pixels, parameters and color context for the same transform at preview/export size. |
| Execution | `src/batch/queue.js`, `src/batch/worker.js` | Start with one heavy job. Transfer buffers where ownership permits. Track job IDs, cancel cooperatively between chunks, and replace a worker for an uninterruptible decode. Ignore stale results. |
| Session and views | `index.html`, `src/ui/session.js`, `src/ui/gallery.js`, `src/ui/preview.js`, `src/ui/controls.js` | Hold immutable automatic recipes, selected mode, named shared layers and per-image overrides. One effective recipe feeds preview and export. Release old object URLs, bitmaps and canvases on replacement, reset or close. |
| Export | `src/export/encode.js`, `src/export/metadata.js`, `src/export/names.js`, `src/export/folder.js`, `src/export/zip.js` | Render, encode, validate output type, write compatible metadata and give each output a stable name and outcome. Direct files commit when the writer closes successfully. ZIP entries remain staged until their archive finalizes and commits to a writable sink or is handed to the browser for download. Track handoff separately from verified file commit. Return a field-level metadata disposition. |
| Preferences and extension | `src/presets/store.js`, `src/imaging/enhancement.js` | Version a small validated settings-only payload. Define a synchronous or asynchronous local enhancement contract that accepts image context and returns a bounded result. The default pipeline uses the correction engine alone. |

Track source analysis separately from export. Each source has a session ID, a normalized relative path within its selected root, a file snapshot and a status. Within the same import root, a repeated unchanged path counts once. When the browser cannot establish root identity across separate selections, keep the selections distinct and report possible duplicates. Keep separate paths even when their bytes match. Sort eligible, deduplicated paths deterministically before admitting 100. Files recognized as candidate formats count toward the cap even when decoding fails. Unsupported files do not count. Keep overflow visible and let users replace a failed slot explicitly. Reuse the retained source snapshot for export. If reopening is needed, verify the original content digest before reusing analysis. If the source becomes unreadable or changes, require reimport and reanalysis. Use transient, incrementally computed digests only where reopening requires them.

An export snapshots the recipe and settings. Identify each output by source, recipe revision, mode, format, and size. Track queued, rendering, encoded, staged, committed, handed off, failed and cancelled outcomes independently of source analysis. Keep full-resolution data limited to the active job and cap preview caches. Give per-image overrides precedence over shared settings. Show automatic confidence alongside a separate effective-recipe warning when manual changes cause measurable clipping or noise.

### Correction and ranking

Analyze thumbnails in an explicit linear working space. Compare a near-identity baseline, clipped robust gray-world or percentile white balance, a bounded Shades-of-Gray variant, and a conservative highlight/shadow and chroma transform. Evaluate low-signal channel denoise before limited gain. Fit a regularized matrix only with valid reference evidence. Local red detail can guide luminance recovery, with uncertain hue desaturated and flagged. Avoid red-equals-neutral, globally forcing skin hues, or treating a clipped channel as a usable reference. Inspect channel percentiles, near-floor signal and near-ceiling fraction, local flat-patch noise, red dominance, saturation and gamut loss. Use deviations on credible neutral/skin regions only when those regions are supported by the observed signal. [Shades of Gray reference](https://library.imaging.org/cic/articles/12/1/art00008), [CSS Color 4 conversions](https://www.w3.org/TR/css-color-4/)

Rank candidates within mode-specific gain, noise and clipping limits. Use a fixed score combining exposure/detail retention, residual cast with credible references, saturation/gamut penalties, noise amplification and artifact flags. Include a conservative baseline and use less invasive recipes as deterministic tie-breakers. Confidence depends on source-channel evidence, severe clipping/noise flags, ranking margin and stability across patches or scales. Weak evidence or conflicting scores should keep confidence low even when the winner has a high rank. Emit explicit reasons and calibrate ordinal categories with reviewer judgments. Aggressive may trade more artifacts for apparent color and must surface that risk. Use human ranking at F3, with paired target comparisons available only for controlled scenes. Compare algorithm–reviewer rank agreement against a fixed simple baseline and record disagreements. Use per-tile disagreement to flag mixed-light scenes where global gains are unstable.

## 5. Technical risks and mitigation strategies

| Risk | Mitigation and decision trigger |
| --- | --- |
| Red-only capture and mixed lighting | Treat rendered linearized RGB as an approximation after the iPhone image pipeline. Under an ideal monochromatic light, independent surface color dimensions are unavailable. Use noise-aware gain limits and low-evidence flags. Test scenes without neutrals, naturally red subjects, mixed illumination and ordinary light. Use human preference to validate the ranking on a held-out set. [Rendered-image white balance research](https://openaccess.thecvf.com/content_CVPR_2019/html/Afifi_When_Color_Constancy_Goes_Wrong_Correcting_Improperly_White-Balanced_Images_CVPR_2019_paper.html), [Gray Edge](https://ivi.fnwi.uva.nl/isis/publications/2007/vandeWeijerTIP2007/), [Mixed illuminant research](https://www.squicky.org/work/sig08lme/) |
| Native HEIC and bundled decoder | Chromium's published image-decoder dispatch does not list HEIC. Verify the current stable Chrome release on Windows 11 and prefer an app-bundled decoder path that works offline. Bound dimensions, total pixels, metadata, decode time and decoder-owned allocations. Validate 8/10-bit HEIC, primary image selection and transforms. Track upstream version and codec distribution obligations, including review of HEVC patent implications for the intended distribution. [Chromium image decoder](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/third_party/blink/renderer/platform/image-decoders/image_decoder.cc), [Chromium HEIC issue](https://issues.chromium.org/issues/41389159) |
| Color and HDR | Define and record primaries, transfer, precision, alpha representation, orientation and conversion ownership at decode, working, preview and export boundaries. Start by evaluating linear Display P3 as the working space for sRGB and P3 SDR sources, with bounded float tiles for math and an explicit gamut mapping when targeting sRGB. Preserve headroom through correction and avoid an intermediate sRGB canvas on the P3 path. Track whether the decoder applied ICC or NCLX color conversion or geometry. Test actual precision, alpha and profile signaling at serialization. Document treatment of untagged profiles, HDR bases and gain maps. Report intentional SDR mapping and dropped HDR data. [W3C CSS Color 4](https://www.w3.org/TR/css-color-4/), [Chrome P3 Canvas](https://developer.chrome.com/blog/new-in-chrome-94), [HTML canvas serialization](https://html.spec.whatwg.org/multipage/canvas.html) |
| Metadata integrity | Inventory original EXIF/GPS, capture time/timezone, ICC/NCLX, XMP, IPTC and applicable proprietary or auxiliary data. Rebuild JPEG APP1 EXIF and APP2 ICC segments as applicable. For PNG validate eXIf, iCCP or compatible standard color signaling, and test XMP carriage. Update orientation to upright and dimensions to exported pixels. Drop or regenerate stale embedded thumbnails and avoid unsafe offset-dependent MakerNote copies. Keep format-specific field-level reasons and distinguish preserved, normalized, unavailable and dropped fields. Verify compatible XMP/IPTC mappings and report any loss. Never reattach source ICC to differently encoded pixels. [PNG 3](https://www.w3.org/TR/png-3/), [CIPA Exif standards](https://www.cipa.jp/e/std/std-sec.html), [ICC specifications](https://www.color.org/icc_specs2.xalter) |
| Output collision and partial writes | Reserve sanitized Windows-safe names case-insensitively and serialize writes per destination. The browser can return an existing handle from a create request. Writer exclusivity does not guarantee exclusive creation. Prefer direct save where a no-overwrite path can be demonstrated. If shared-folder creation is unsafe, offer a fresh dedicated directory only if its creation and write guarantees are demonstrated. Otherwise use ZIP. Retry only outputs that did not commit or explicitly selected uncertain handoffs, keeping the original settings snapshot and stable filenames where safe. On failure, abort the current write and clean up only artifacts proven to belong to that attempt. If a ZIP fails before finalization, stage its entries again on retry. Keep committed earlier volumes and distinguish download handoffs from durable commits. [File System Standard](https://fs.spec.whatwg.org/#api-filesystemdirectoryhandle-getfilehandle) |
| 100-photo memory and fallback | One 48 MP RGBA8 buffer costs roughly 183 MiB before canvas, decoder heap, browser copies or GPU resources. Use one heavy photo at a time, avoid full-frame float intermediates, transform by row/tile where practical and release full-resolution buffers on every exit path. Measure browser process and GPU memory in addition to JS heap. Track temporary disk consumption because Chromium may back large Blobs on disk. [Chrome memory tooling](https://developer.chrome.com/docs/devtools/memory-problems), [Chromium Blob storage](https://chromium.googlesource.com/chromium/src/+/HEAD/storage/browser/blob/README.md) ZIP streaming controls producer memory only if the sink drains it. Test writable destinations and actual Blob downloads. If needed, propose bounded complete ZIP volumes with a clear sequence and approve their UX before adoption. Every selected output must remain available without quietly resizing or discarding it. |
| Privacy and offline security | Package verified local artifacts with no analytics, network requests, uploads, background sync or service workers. Evaluate a restrictive CSP with narrowly required local, Blob and WASM sources. Render filenames as text, validate container sizes before allocation, isolate expensive decodes in a worker, pin audited dependencies and prevent user content from entering logs, settings, history or URLs. Keep folder permissions and photos in session memory. Document that explicitly saved outputs and retained GPS are visible to their recipients, and that browser-managed temporary backing can exist during processing. Keep browser-managed artifacts out of claims about the app’s own persistence. |
| Settings and browser policy | Storage behavior for a file URL is undefined across implementations. Test stable path/profile, restart, denied or cleared storage and relocation. Document quotas and recovery. Browser policy can disable writing, so exercise the fallback in Chrome with write access denied. [MDN localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage), [Chrome File System Access](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access) |

## 7. Detailed implementation phases 2 through 6

### Phase 2 · Correction engine

- **Objective and dependencies.** Deliver a deterministic single-image processing core. Requires approved Phase 1 findings, canonical color/orientation contract and quality rubric.
- **Tasks and expected files.** Implement selected decoder/color adapter in `src/imaging/loader.js` and `color.js`. Implement robust channel statistics, candidate transforms, mode bounds, ranking, confidence reasons and the future enhancement boundary in `src/imaging/{analyzer,correction,quality,enhancement}.js`. Keep controls as serializable recipes and render reduced previews with the same math used for later full-resolution exports.
- **Testing and acceptance.** `tests/imaging/` verifies finite math, tie breaks, deterministic results, neutral/strong-cast behavior, low signal, clipping, noise and mixed-light disagreement. Run the approved F2/F3/F7 corpus relevant to this stage. All valid supported inputs decode through the approved pixel contract. Each mode generates a recipe, automatic confidence and explanations, and the ranker and confidence meet their separate F3 criteria.
- **Deliverables, risks and approval.** Core, sample comparisons and quality report. Watch for overfit and noise amplified by gain. Obtain user approval of image quality before Phase 3.

### Phase 3 · Interface

- **Objective and dependencies.** Deliver the review and adjustment workflow on a single image, with collection state ready for batching. Requires Phase 2 recipes and status/reason contracts.
- **Tasks and expected files.** Build `index.html`, `styles/app.css` and `src/ui/{session,gallery,preview,controls}.js`. Show thumbnails, selected preview and side-by-side views with accessible names and keyboard controls. Add low-confidence filter, mode selection with Aggressive indication, simple controls and expandable advanced controls. Label automatic confidence with its mode and show independent warnings for artifacts introduced by the effective recipe. Model individual, selected and batch scopes, layer precedence/reset and error/status presentation. Use simulated collection state where Phase 4 processing is a dependency.
- **Testing and acceptance.** `tests/ui/` covers keyboard selection, filter, focus, failure states, three modes, scope application and reset on a prepared collection. Verify changing A individually leaves B and automatic recipes intact, shared scoped changes affect exactly selected IDs, and enlarging or changing selection does not retain stale previews. Verify that a manual change can trigger an artifact warning without changing automatic confidence. In Chrome, a user can complete the single-image workflow and understand the displayed confidence reasons.
- **Deliverables, risks and approval.** Usable review workflow and UI walkthrough. Guard against misleading confidence wording and hidden override precedence. Obtain user interface sign-off before Phase 4.

### Phase 4 · Batch and export

- **Objective and dependencies.** Complete the import-to-output workflow. Requires Phase 3 interaction model and Phase 1 picker, encoder, color, metadata and archive decisions.

- **Testing and acceptance.** `tests/batch/` and `tests/export/` exercise 100 mixed photos, cap overflow, malformed inputs, retry, cancellations, collisions, existing inputs/outputs, denied permissions and archive validity. Successful analysis and committed output survive unrelated failure or retry. Uncommitted archives are recreated and uncertain download handoffs remain visibly separate.

## 9. Testing and quality assurance strategy

- **Fixtures.** Keep synthetic fixtures or expressly consent-cleared non-sensitive inputs. Give each fixture a manifest ID, provenance, expected outcome and hash. Include malformed and high-dimension samples, ordinary and red-light images, alpha, profile and orientation variants, duplicate paths and generated metadata. Keep holdout quality fixtures separate from tuning and avoid private data in evidence artifacts.
- **Unit and integration.** Verify transform determinism and score boundaries, stride/orientation/color math, adjustment precedence, queue transitions, worker termination, metadata individually and filename reservations. Exercise actual decoder-to-export paths with mixed batch input, repeat/cancel/retry, archive inspection and independent viewer reopening.
- **Manual browser validation.** Verify stable Chrome on Windows 11 at the recorded version in the supported launch mode with network disconnected, real folder dialogs and OS extraction. Include denied picker permissions, browser policy, download prompts, settings reset, keyboard accessibility and error recovery.
- **Independent checks.** Use reference decoding, ExifTool tags, calibrated color patches, hash comparisons and approved blind human review. Measure responsiveness, live allocations, process/GPU memory and temporary archive disk growth. Capture reproducible evidence before and after relevant optimizations.
- **Regression.** Keep fixtures and golden structural assertions versioned. Use tolerances for browser codec outputs and perceptual color. Repeat focused tests after library/browser changes and the full matrix for packaging. Track severity and assign unresolved core failures to a phase gate.

## 13. Recommended implementation sequence

1. Review this plan and separately authorize Phase 1, including the proposed test thresholds, Windows baseline and permitted fixtures.
2. Smoke-test launch first, then run the integrated decode, color, metadata, quality, export and privacy scenarios in §6 before issuing the final launch verdict. Publish findings and obtain approval of the architecture and dependency choices.

Every approved v1.0 behavior in Review A remains essential.
